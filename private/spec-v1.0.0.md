# Спек: MyLife-AI v1.0.0 — первый публичный релиз

> Синхронизировано с `private/docs/adr/0001-0004` и `private/PLANNING.md`. Трекер задач не настроен — спек хранится файлом, не опубликован. Когда появится трекер (см. `/setup-matt-pocock-skills`), перенести с лейблом `ready-for-agent`.
>
> **Ревизия 24.09 (вечер)**: обновлено под новые реалии — репозиторий пересоздан с нуля через `create-next-app` (не скопирован из старого), гейтинг реализован компонентом, а не middleware, добавлен процесс ручного постраничного переноса кода с участием владельца.

## Problem Statement

Есть два связанных, но разных барьера перед публичным релизом.

Первый — продуктовый: часть страниц выглядит недоделанной/странной для постороннего посетителя, история версий смешивает эксперименты с тем, что можно показывать людям, а единого способа сказать «этот раздел ещё не готов» не было.

Второй — обнаружился по ходу работы и оказался важнее: **весь существующий код целиком написан Claude Code**, владелец проекта (без опыта в JS/TypeScript/React) в нём не ориентируется и не может самостоятельно ни поддерживать, ни объяснять свой же продукт — критично для коммерческих планов и для будущей работы с университетской командой.

## Solution

Часть 1 (продукт, v1.0.0): переработанный лендинг как единственная полноценно видимая страница, остальные разделы (`/onboarding`, `/profile`, `/weight`, `/measurements`) управляются единым реестром статусов (`live` / `placeholder` / `hidden`), решение о показе реального контента / заглушки принимается **на уровне самой страницы** (не middleware — см. Implementation Decisions), одинаково для захода через меню и напрямую по ссылке.

Часть 2 (процесс, применяется прямо сейчас): проект пересоздан с нуля через официальный `create-next-app` в новой папке, вместо переноса старого репозитория как есть. Старый код (полностью рабочий, v0.7.0) переносится обратно **вручную, файл за файлом**, с объяснением каждого шага — так владелец реально понимает, что у него в проекте, а не просто получает работающий сайт от ИИ во второй раз.

## User Stories

1. Как посетитель, я хочу видеть аккуратный переработанный лендинг, чтобы продукт выглядел как реальный, а не как прототип.
2. Как посетитель, я хочу, чтобы меню показывало только реально работающие разделы, чтобы не натыкаться на сломанные экраны.
3. Как посетитель, я хочу видеть понятное сообщение «в разработке», если открываю недоделанный раздел, чтобы не думать, что сайт сломан.
4. Как посетитель, попавший на скрытый раздел напрямую по ссылке (не через меню), я хочу видеть тот же корректный результат (заглушку или 404), а не сырой недоделанный экран.
5. Как владелец продукта, я хочу, чтобы все коммиты и push были подписаны только мной, чтобы в репозитории не было следов ИИ-инструментов — включая файлы, которые сам Next.js создаёт автоматически (`AGENTS.md`, `CLAUDE.md`).
6. Как владелец продукта, я хочу чистую историю коммитов, начинающуюся с v1.0.0, чтобы не объяснять и не вычищать прежние экспериментальные коммиты.
7. Как владелец продукта, я хочу единый источник истины о статусе каждой страницы (`live`/`placeholder`/`hidden`), чтобы менять видимость раздела в одном месте.
8. Как владелец продукта, я хочу, чтобы логика статуса применялась независимо от точки входа (меню/прямой URL), чтобы недоделанные страницы никогда не показывались случайно.
9. **Как владелец продукта без опыта в JS/TS/React, я хочу сам, вручную, файл за файлом, воссоздать проект из уже написанного кода, с пояснениями на каждом шаге, чтобы реально понимать, что происходит в моём собственном продукте.**
10. **Как владелец продукта, я хочу видеть прогресс сразу в браузере на каждом значимом шаге переноса, чтобы не терять ощущение, что что-то реально получается.**
11. Как владелец продукта, я хочу, чтобы репозиторий пока оставался приватным, чтобы код не был публично виден, пока продукт ещё формируется.
12. Как будущий участник команды, я хочу менять статус страницы в одном очевидном месте, чтобы быстро разобраться в проекте.
13. Как будущий участник команды, я хочу обычный collaborator-доступ и коммитить под своим именем, чтобы мой вклад был корректно атрибутирован.
14. Как владелец продукта, я хочу, чтобы `/onboarding`, `/profile`, `/weight`, `/measurements` не терялись при переносе, даже если в v1.0.0 они скрыты или показаны как заглушка.
15. Как владелец продукта, я хочу, чтобы новый лендинг заменил текущий (который «выглядит как ИИ»), чтобы первое впечатление соответствовало реальному коммерческому продукту.
16. Как посетитель, я хочу получить связный опыт независимо от устройства, чтобы оценить продукт и с телефона, и с компьютера.
17. Как владелец продукта, я хочу, чтобы механизм гейтинга страниц было легко расширить на будущие auth/подписочные проверки, чтобы при появлении бэкенда (Postgres/Auth.js) не пришлось переделывать архитектуру доступа.
18. Как владелец продукта, я хочу, чтобы версии релизов шли по схеме MAJOR.MINOR.PATCH начиная с v1.0.0, чтобы масштаб изменений в релизах был понятен.
19. **Как владелец продукта, я не хочу тащить в новый проект неиспользуемые зависимости (Three.js/@react-three) просто потому, что они были в старом `package.json` — добавлю, когда реально дойду до 3D-модели.**

## Implementation Decisions

- Репозиторий: приватный, `RuDeNoID814/MyLife_Ai` на GitHub (не `MyLife-AI`, как предполагалось изначально).
- **Проект пересоздан с нуля** через `npx create-next-app@latest` (TypeScript, ESLint, Tailwind CSS, `src/` directory, App Router, дефолтный import alias `@/*`), а не скопирован из старой папки — старая версия сохранена нетронутой отдельно как источник для ручного переноса.
- `.claude/`, `CLAUDE.md`, `AGENTS.md` — в `.gitignore`. Важная деталь: `AGENTS.md` и его спутник `CLAUDE.md` (короткий файл-указатель `@AGENTS.md`) **пересоздаются самим Next.js** при каждом запуске `next dev` — это не разовая генерация, гитигнор должен быть постоянным, а не разовой чисткой.
- Three.js/@react-three/drei/fiber — были в старом `package.json`, но нигде не использовались в реальном коде (проверено `grep` по всему `src/`, совпадений ноль; папка `model/` для файла самой 3D-модели даже не была создана). В новый проект не переносятся; добавляются отдельным шагом, когда реально начнётся работа над 3D-моделью.
- **Реестр статусов страниц**: конфиг-модуль (маршрут → `status: 'live' | 'placeholder' | 'hidden'` + лейбл) — без изменений по сути, уже реализован и протестирован в старом коде (`src/lib/pages.ts`).
- **Гейтинг — НЕ через `middleware.ts`.** Обнаружено техническое ограничение: проект использует `output: 'export'` (static export, осознанное решение с первого дня — нужно для Vercel-хостинга и будущего мобильного порта через Capacitor), а Next.js Middleware в этом режиме не работает вообще. Вместо этого гейтинг реализован компонентом `<PageGate route="...">`, который каждая страница сама оборачивает вокруг своего содержимого: `hidden` → вызывает `notFound()` (стандартный 404), `placeholder` → рендерит общий `<PlaceholderPage>`, `live` → рендерит переданный контент. Поскольку весь сайт всё равно «запекается» в статические файлы на этапе сборки, разницы между заходом через меню и напрямую по URL физически не существует — сервера, который мог бы их различать, нет.
- `<SiteNav>` — читает тот же реестр, рендерит только `live`/`placeholder`-пункты; заменяет задублированные инлайн-блоки `NavPill` (ещё предстоит перенести).
- Присвоение конкретного статуса (`placeholder` vs `hidden`) каждому из `/onboarding`, `/profile`, `/weight`, `/measurements` — по-прежнему открытое решение владельца, не зафиксировано.
- Редизайн лендинга — визуальное направление не фиксируется заранее, прорабатывается итеративно по фидбеку владельца.
- **Процесс переноса кода**: владелец переносит/пересоздаёт файлы вручную, по одному, в порядке от фундамента к видимому — сначала `lib/`/`db/`/`components/` целиком (без новых концепций, просто перенос уже рабочего кода), затем страницы по одной, начиная с лендинга. Автотесты (Vitest) переносятся отдельным, более поздним этапом — после того как всё приложение уже работает в чистом виде.
- Бэкенд/БД не реализуются в этом спеке (см. ADR 0003/0004); архитектура `PageGate` допускает расширение на auth-проверки позже без переделки.
- Участники команды при подключении получают стандартный collaborator-доступ, коммитят под своей личностью.
- Никаких AI co-author трейлеров или иных следов ИИ-инструментов ни в одном коммите этого репозитория.

## Testing Decisions

- Хороший тест проверяет внешнее поведение, а не реализацию: дан маршрут со статусом Y → проверяем итоговый рендер (реальный контент для `live`, `<PlaceholderPage>` для `placeholder`, `notFound()` вызван для `hidden`) — не то, как `<PageGate>` это вычисляет внутри.
- Модули с тестами (уже написаны в старом коде, ждут переноса): `src/lib/pages.ts` (реестр — node-окружение), `src/components/PlaceholderPage.tsx` и `src/components/PageGate.tsx` (jsdom-окружение, через `@testing-library/react`).
- Прежний опыт в проекте: Vitest настроен с разделением на `lib` (node) и `ui` (jsdom) окружения; для jsdom-проекта потребовался `@vitejs/plugin-react` и `@testing-library/jest-dom` — их до этого в проекте не было (это были первые в проекте `.tsx`-тесты).
- **Явное решение по срокам**: тесты не переносятся вместе с остальным кодом — откладываются на отдельный этап после того, как всё приложение будет перенесено и будет работать в браузере. Причина — не перегружать владельца ещё одной новой концепцией («программа, которая проверяет другую программу») одновременно с изучением остального стека.
- Вне автотестов: визуальный/контентный редизайн лендинга и сама настройка репозитория/git.

## Out of Scope

- Бэкенд, БД, аутентификация (Postgres/Prisma/Auth.js/MinIO) — отложено по ADR 0003/0004.
- Конкретный визуальный дизайн переделанного лендинга — прорабатывается итеративно вне этого спека.
- Финальное присвоение `placeholder` vs `hidden` для каждой из 4 нелендинговых страниц — решение владельца, ещё не принято.
- Three.js/3D-модель тела — сознательно не переносится сейчас, отдельная будущая задача.
- Автотесты — отдельный более поздний этап (см. Testing Decisions).
- Процесс онбординга университетской команды — отложено до одобрения проекта по английскому.
- VDS-хостинг, Docker Compose деплой — будущая работа.
- Перенос/чистка истории старого репозитория — отменено ADR 0001 в пользу нового репозитория с нуля.
