# Гейтинг страниц — компонент `<PageGate>`, не middleware

В грилле по v1.0.0 изначально выбрали middleware (`middleware.ts`) как шов для гейтинга страниц (`live`/`placeholder`/`hidden`) — так и уровень был бы один на все маршруты, и задел на будущие auth-проверки.

При реализации (тикет 02) выяснилось: проект использует `output: 'export'` (static export) — осознанное решение с первого дня (`docs/tech-stack.md`), нужное для Vercel-хостинга без сервера и будущего мобильного порта через Capacitor. **Next.js Middleware не работает в режиме static export вообще** — сборка либо падает, либо middleware просто не запускается, сервера, который мог бы его исполнять, нет.

Решено: гейтинг реализован компонентом `<PageGate route="...">`, которым каждая страница оборачивает своё содержимое. `hidden` → `notFound()` (стандартный 404), `placeholder` → `<PlaceholderPage>`, `live` → передан контент как есть. Реестр статусов (`src/lib/pages.ts`) остался общим и не изменился.

Побочный эффект, снявший исходную причину выбрать middleware: при static export весь сайт «запекается» в статические файлы на этапе сборки — разницы между заходом через меню и прямым URL физически не существует (нет сервера, который мог бы их различить), так что задача «одинаковое поведение независимо от точки входа» решается и на уровне компонента, без потери исходной цели.

**Consequence**: когда появится реальный бэкенд/auth (см. ADR 0003/0004), тогда же придётся отказаться и от static export — на этом этапе имеет смысл пересмотреть, не вернуться ли к middleware для auth-гейтинга, раз сервер уже будет.
